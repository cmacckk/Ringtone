# M6 · 提醒渠道选择（每条任务选发到钉钉 / 飞书 / 全部）

## 一、目标与语义

用户要求：**添加任务时可以选「发钉钉」「发飞书」还是「全部」**；并额外确认了一条行为——
只勾了一个渠道而它发失败时，**只走本机通知兜底 + 记一条失败，不偷偷发到另一个渠道**。

三层语义：

| 层 | 表示 | 含义 |
| --- | --- | --- |
| 数据库 | `tasks.notify_channels TEXT` | `NULL` = 不限制（发全部启用渠道）；`'["dingtalk"]'` = 只发这些**类型** |
| 接口 | `TaskInput.notify_channels: Option<String>` | `None` = 不限制。与 `remind_offsets` 的 `None` **不是一个意思**（那个是「保持原值」，这个是真实取值） |
| 界面 | 添加/编辑行上的「通知：钉钉 / 飞书」开关 | 全开 = 存 `null`；只开一部分 = 存类型列表 |

界面行为：

- **至少留一个**：全关等于「一条都不发」，没有这个选项，所以最后一个开关点不动；
- 全开时存 `null`（不限制），这样以后新增渠道会自动包含进去，而不是把当前这两个渠道钉死；
- 只配了 **1 个**启用渠道时开关整个不显示（没得选，发不发是渠道自己的启用开关管的）；
- 选过的渠道后来被停用时，开关旁灰字提示「钉钉已停用」，列表行标签的 tooltip 也写明会走本机通知兜底；
- 列表行显示 `仅钉钉` 这类标签（走 `KIND_LABEL` 取中文名），不限定渠道的任务不显示标签。

## 二、设计取舍（为什么这么写）

1. **存渠道类型，不存渠道 id**。渠道可以在设置里删掉重建，`channels.id` 会变；按 id 存的话，
   用户删一次钉钉渠道就会让所有「只发钉钉」的任务变成「一个都不发」。
2. **不校验「这个类型认不认识」**。`channel/mod.rs` 里有明确约定：不提供 kind 常量表（免得界面出现
   「填了也发不出去」的选项），配置是运行时读的。所以只卡形状（JSON 字符串数组、非空、≤8 个、去重、trim）。
   认不出的类型在发送时找不到渠道 → 走本机通知兜底，**不会静默丢提醒**。
3. **更新时直接覆盖，不用 `COALESCE`**。`remind_offsets` 用 `COALESCE(?n, remind_offsets)` 是因为
   那里的 `None` 表示「界面没碰、保持原值」；这里的 `None` 是「全部渠道」这个真实取值，
   用 COALESCE 就再也改不回「全部」了。
4. **降级只在勾选的渠道里降**。`deliver.rs` 的降级分支原来查「全部启用渠道」，会让「只勾钉钉」的任务
   在钉钉失败时悄悄发到飞书 —— 与用户明确的选择冲突。现在降级查询同样走
   `db::channels_for_occurrence`，允许列表为空就老老实实走到「全渠道失败」分支：本机通知 + 记一条失败。
5. **同一个选择只存一种写法**。`normalize_notify_channels` 会 trim、去重、`sort()` 之后再序列化，
   所以「先点钉钉再点飞书」和「先点飞书再点钉钉」在库里是同一个字符串，比较/测试都不会被顺序坑到。
6. **坏值一律当「不限制」**（`parse_notify_kinds`）。宁可多发一条，也不要因为库里的一个脏值变成
   「这个任务永远不提醒」。

### 失败注入：只勾钉钉 + 把钉钉改坏

按用户要求真跑了一遍「只勾一个渠道、它又发失败」的路径（不是单测）：把钉钉渠道的 `access_token` 换成错的
（加签密钥保持正确），插一条 `notify_channels='["dingtalk"]'`、50 秒后到点的任务，**飞书保持启用**——如果代码降级
逻辑写错了，它就会偷偷发到飞书去。

```text
[ringtone] 已入队：失败注入·只发钉钉（occ=119 late=false）→ 「钉钉」
[ringtone] 全渠道失败，已用本地通知兜底：失败注入·只发钉钉（[Auth/HTTP 200] 钉钉返回 errcode=300005 errmsg=token is not exist）
[ringtone] 投递本轮：成功 0 / 退避 0 / 降级 0 / 限流推迟 0 / 全渠道失败 1
[ringtone] 托盘状态：1 条提醒发送失败（红点已显示）
```

| 该看的 | 实测 | 结论 |
| --- | --- | --- |
| 入队的渠道 | 只有「钉钉」 | 任务级限定生效 |
| 错误分类 | `[Auth/HTTP 200] errcode=300005 token is not exist` | 判为不可重试 → 不傻等退避（没有 5s/30s/2min 三次重试） |
| 有没有降级到飞书 | `降级 0`，飞书 **当天发送计数没涨**（仍是 1，那 1 是前面「只发飞书」测试的） | 没偷偷发到另一个渠道 |
| 本地兜底 | `全渠道失败，已用本地通知兜底`，实例 `state=sent`、`sent_ms - fire_at_ms = 3025 ms` | 兜底成功，且仍在「到点 ±5 秒」内 |
| 记一条失败 | `push_jobs.id=14 state=failed attempts=1 last_error=[Auth/HTTP 200] …300005…`；托盘红点 `1 条提醒发送失败` | 记账 + 红点都在 |
| 钉钉有没有被改坏到留下痕迹 | 跑完立即按备份逐字节还原，`config_json` 与备份一致 | 渠道配置已复原 |

测试任务 42 / 实例 119 / 作业 14 已按明确 id 删除；`send_log` 里那两条记录（失败 + 本地兜底）保留。

## 五、这一轮踩到的坑

1. **`task_at` 测试辅助的字面量补丁把闭包 `},` 一起删掉了** → `error: mismatched closing delimiter: )`（`db.rs:1724`）。
   原因是用 `edit` 改一整个结构体字面量时，`oldText` 的末行带 `},` 而 `newText` 没带。教训同上次：
   **不要把「只差一行括号」当成无害差异**。
2. **用户报的「今日进度停在昨天」不是统计算错，是系统时钟被校准了**：排查时本机 `date` 是
   `2026-10-08 17:30`，而网络时间（baidu / taobao 的 `Date` 响应头）已经是 `10-09 07:32`；
   几分钟后本机自己跳到 `10-09 08:17`。App 的「今天」取系统时间，所以老老实实按 10-08 统计。
   真正的问题是**界面只在挂载时算一次「今天」**（托盘常驻窗口跨天不刷新），已修：
   30 秒核一次 `today_local()`，变了就刷（正看着「今天」就一起挪过去）。实测周条高亮变成 `周五 10-09`、
   今日进度 `0/3`。

## 七、已知缺口

1. **`send_log` 少了「渠道本身失败」那一行（本轮注入时发现，待修）**：`deliver.rs` 的 `exhaust()` 里那句注释写着
   「渠道的失败已经在降级时逐条写过了」——这句话**只在「降级到下一个渠道」时成立**。当允许列表里没有下一个渠道
   （就是「只勾一个渠道」这种情形）时代码是 `None => return exhaust(...)`，**根本没写过渠道失败行**。
   实测 `send_log` 里只有一条 `channel=null result=sent`（本地兜底），钉钉那次失败只留在 `push_jobs.last_error`。
   用户能看到的「发送记录」因此丢了渠道归属（原因文字还在，但不算在钉钉头上）。修它要动 Rust、
   会触发应用重建重启，所以先记在这里，等确认。
2. 开关只在配了 **2 个以上**启用渠道时出现；只配一个渠道时用户没得选。
3. 选中渠道被停用/删除时**不会自动改发**到别的渠道（这是故意的），但界面只在标签 tooltip 里说明，
   没有更醒目的提示。
4. 界面上的开关没有自动化用例（项目还没有前端测试框架），这轮靠 CDP 手工脚本 + 库回读验证。
