# Ringtone · M4 里程碑报告（钉钉 + 投递队列 + 降级链 + 限流）

日期：2026-10-08 ｜ 状态：✅ 完成并有实测证据 ｜ 上一步：[M3 飞书渠道](./M3-report.md)

## 一句话结论

到点后的提醒现在走**队列**：先发主渠道，发不出去按**错误类型**决定「等一会儿重试」还是「立刻换下一个渠道」，
全渠道都失败才用本机通知兜底，并在托盘和界面上留一个**看得见的失败角标**——不会静默丢。

渠道范围按你的决定收敛为**钉钉 + 飞书**两个（Server 酱弃用、PushPlus 因收费取消）。

## 实测证据（真跑）

### 1. 钉钉真发出去了（含加签）

| 项目 | 值 |
| --- | --- |
| 渠道 | 钉钉机器人 webhook + 加签密钥 |
| 结果 | `errcode=0`（签名不对时钉钉会回 `errcode=310000`，所以这是加签正确的铁证） |
| **网络耗时** | **232 ms** |
| **到点后送达** | **2844 ms**（含最多 2 秒的调度网格） |

### 2. 降级链：钉钉坏了，飞书接手

把钉钉 webhook 的 `access_token` 改成假值 → 钉钉回 `errcode=300005 token is not exist`（HTTP 200）→ 被判定为**凭证类错误、不可重试** → **当场**改投飞书：

```text
[ringtone] 发送失败已降级：M4 冒烟·降级链（[Auth/HTTP 200] 钉钉返回 errcode=300005 errmsg=token is not exist，第 1 次）→ 改投「飞书」
[ringtone] 已发送：M4 冒烟·降级链 → 飞书：message_id=om_x100b63406d3e9ca4b03268ce4cf1f99
```

### 3. 退避重试：第一次 500，第二次成功

用本地测试桩假装钉钉（第一次返回 HTTP 500，之后返回 `errcode=0`）：

| 事件 | 时刻 | 说明 |
| --- | --- | --- |
| 第 1 次投递 | `07:31:06.010` | HTTP 500 → 判定「可重试」 |
| 第 2 次投递 | `07:31:12.025` | 间隔 **6.0 秒** = 5 秒退避 + 最多 2 秒网格对齐 → HTTP 200 成功 |

```text
[ringtone] 发送失败将重试：M4 冒烟·退避重试（[Retryable/HTTP 500] …，第 1/4 次，5000 ms 后）
[ringtone] 已发送：M4 冒烟·退避重试（occ=84 attempts=2 网络 21ms 到点后 9481ms）
```

### 4. 全渠道失败 → 兜底 + 红点

只剩一个渠道且它回凭证类错误时：

```text
[ringtone] 全渠道失败，已用本地通知兜底：M4 冒烟·退避重试到耗尽（[Auth/HTTP 200] 钉钉返回 errcode=300005 …）
[ringtone] 托盘状态：1 条提醒发送失败（红点已显示）
```

`send_log` 记 `result=failed`，`detail` 保留渠道原始错误码；托盘换成红点图标、tooltip 变成 `Ringtone · 1 条提醒发送失败`；界面右上角出现 `⚠ 1 条没发出去`。

### 5. 到点延迟达标（修掉一个真实缺陷之后）

用「停用全部渠道 + 插一排相差 1 秒的任务」做探针，回读 `sent_ms` 就能直接看出调度网格：

| 到点 | 实际触发 | 延迟 |
| --- | --- | --- |
| 15:21:55.233 | 15:21:56.003 | 770 ms |
| 15:21:56.233 | 15:21:58.007 | 1774 ms |
| 15:21:57.233 | 15:21:58.009 | 776 ms |
| 15:21:58.233 | 15:22:00.007 | 1774 ms |
| 15:21:59.233 | 15:22:00.009 | 776 ms |
| 15:22:00.233 | 15:22:02.005 | 1772 ms |

触发时刻严格 2.000 秒一格 → **最坏延迟 1950 ms**，满足「到点 ±5 秒」。

## 修掉的 3 个真实缺陷（都不是测试写错）

| 缺陷 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 每轮 tick 都刷托盘 | 单轮耗时 5 秒级，到点延迟翻倍（实测 10.8 秒） | 后台线程里无条件调 `set_tooltip` / `set_icon`，要等主线程 | 只在失败条数真的变化时才碰托盘 |
| tick 相位漂移 | 偶发延迟 6.5 秒（= 5 秒 + 1.5 秒），此后再也不回到网格 | `sleep(固定间隔)` 会把一次卡顿永久累积进相位 | 睡到「下一个网格边界」；间隔从 5 秒改为 **2 秒**（最坏延迟 = 间隔） |
| 钉钉 host 被改写 | 用户填的任何 host 都被换成官方域名，自建网关用不上，也没法测「不可达」 | `build_url` 只取 `access_token`，host 写死 | 配了完整 URL 就原样用，只有裸 token 才拼官方地址 |

顺带把「本机通知兜底」和「渠道失败」两个时刻拆开记录：成功日志现在同时打**网络耗时**和**到点后耗时**
（`网络 232ms 到点后 2844ms`）—— 两个数混在一起时，一次慢请求会被误读成「调度不准」。

## 关键设计决定（以及为什么）

| 决定 | 理由 |
| --- | --- |
| 投递走**队列**（`push_jobs` 表），不在 tick 里同步发 | 退避要等 5s/30s/2min，在调度线程里 sleep 会拖住其它提醒；落库才能在重启后知道「哪些没发完」 |
| 错误分类决定行为：`Retryable` 退避重试 / `QuotaExceeded`·`Auth`·`BadRequest`·`Config` 立刻换渠道 | 凭证失效重试一百次也没用；而撞限流继续发会被钉钉封 10 分钟 |
| 速率闸门（内存滑动窗口 60 秒）超限就**推迟**，不算一次尝试 | 钉钉每机器人 **20 条/分**，超了封 10 分钟——这是所有渠道里最硬的一条限制。推迟不消耗重试次数，否则限流会把重试机会吃光 |
| 同渠道内退避重试，跨渠道**不重试直接降级** | 一个渠道整体挂掉时，把 3 次重试机会花在它身上是浪费（实测凭证类错误 1 次就够判断） |
| 一条实例在别的渠道还有排队作业时，成功那条会把其它作业作废 | 否则降级会开出多条支线，同一条提醒收到好几遍 |
| 启动时把「上次中断的 sending 作业」判失败、实例标 `missed`，**不补发** | 你明确要求「关机后不需要再提醒」 |
| 不做「60 秒内多条合并成一条摘要」 | 合并要用延迟换额度，和「到点 ±5 秒送达」直接冲突；单用户场景也撞不到 20 条/分 |

## 尚未验证 / 已知缺口

1. **钉钉 20 条/分的限流闸门没有做真实压测**（要连发 21 条真消息才能碰到，代价太大）。
   闸门的逻辑由单测覆盖（第 21 条会算出「还要等多久」），但「真被钉钉限流时的表现」没实测。
2. 界面上「验证凭据」「发测试消息」「设为主渠道」按钮**没有自动化用例**，请你手点一次确认。
   注意：**钉钉没有「只验证不发消息」的接口**，所以钉钉那一栏的「检查配置」只做格式校验，文案里已说明。
3. 飞书一次发送的网络耗时约 2.9 秒（取 token + 发消息两次请求，每次都新建连接、重新 TLS 握手），
   明显慢于钉钉（232 ms）。仍满足 ±5 秒，但 M5 可以做成复用同一个 HTTP 客户端。
4. 密钥仍是明文存在本机 SQLite（M5 接 Windows DPAPI）。
5. 数据库里留了 M2–M4 的冒烟测试任务（`M2 冒烟*`、`M3 冒烟*`、`M4 冒烟*`、`tick 探针*`），没删——等你发话。
